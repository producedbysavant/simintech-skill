# Встроенный язык SimInTech

Справочник целиком: `https://github.com/producedbysavant/simintech-code/blob/main/` (`language/`, `blocks/`,
`patterns/`, `tutorials/`). Здесь — то, что чаще всего ломает работу агента.

**Официальная справка:**
[Язык программирования SimInTech](https://help.simintech.ru/11_yazyk_programmirovaniya/KEY_yazik_programmirovania.html)
— первоисточник по синтаксису и функциям.

## Когда нужен этот язык

Рекомендованный вендором путь построения схемы скриптом: `createblock`,
`createmodel`, `savemodeltofile` (разбор — в разделе «Построение модели
встроенным языком» ниже). Нужен он и для классов, которые отвергает
библиотека: сейчас такой класс один —

- «Порт выхода»

`CreateBlock` его создаёт — с ненулевым id (замерено 2026-09-18), — но
годность в расчёте не проверена, и отказ идёт от библиотеки, а не от COM.
Блок `Из памяти` этот запрет нёс до 05.10.2026: годность подтверждена замером
(пара памяти считает, значение ходит), запрет снят — блок создаётся и через
MCP.

См. набор `UNSUPPORTED_COM_BLOCK_CLASSES` в
[`simintech_api/constants.py`](https://github.com/producedbysavant/simintech-code/blob/main/simintech_api/constants.py).
Синтаксис `файл.py:ИМЯ` якоря на символ в GitHub не работает — ссылка даёт 404.

Блоки библиотеки «Конечные автоматы» языку **не** требуются: они создаются
через `CreateBlock` — но только по полному имени записи с префиксом
«Конечные автоматы - » (например, `Конечные автоматы - Флаг входа в
состояние`); короткий заголовок с палитры (`Флаг входа в состояние`)
`CreateBlock` не принимает. Собрать автомат целиком через MCP всё равно нельзя
(состояния живут на внутренней странице карты) — см. скилл
`simintech-model-building`.

## Синтаксис — Pascal, не C

**Самая частая ошибка** — писать C-подобный код.

| Неправильно (C) | Правильно (SimInTech) |
|---|---|
| `==` | `=` |
| `!=` | `<>` |
| `&&` `\|\|` `!` | `and` `or` `not` |
| `{ }` как блок кода | `begin ... end;` |
| `//` в конце строки без `;` | обязательна `;` |

Полный набор операторов:

- арифметика: `+ - * /`, `div` (целочисленное), `mod` (остаток)
- сравнение: `= <> < > <= >=`
- логика: `and or not xor`
- биты: `shl shr`

## Циклы, `exit` и секции трансляции

**`for` — «конечный цикл», форма со скобками и запятыми** (справка вендора,
`.../5_klyuchevye_slova/podprogrammy/for.html`):

```simintech
for (idx = 1, 10) sum = sum + idx^2;  // шаг 1 (или -1, если конец меньше начала)
for (coef = 0.1, 1, 0.2) begin ... end;  // шаг — третьим параметром
```

Имена в примерах — от трёх знаков и не `i`/`j`/`c`: кодогенерация резервирует
их под свои счётчики (см. чек-лист в `simintech-langblock`); справка вендора
пишет переменную цикла как `i`, но в транслируемом коде так нельзя.

Паскалевская форма `for i := 0 to N` **средой не принимается** (живой прогон
06.10.2026: контурное тело с ней не собралось, «тело не собралось»). В телах
контуров MCP поэтому работает `while` с явным счётчиком — он проверен живыми
прогонами; форма `for (idx = 0, N)` в контуре ещё не пробовалась.

`while <условие> do begin … end;` — цикл с предусловием; `repeat … until
<условие>;` — с постусловием (обе формы — справка вендора).

`exit` — досрочный выход из текущего программного блока (например, из тела
под условием ошибки: выставить выходной сигнал-диагностику и `exit`).

**Секции исключения из трансляции.** Операции между `disabletranslate` и
`enabletranslate` исключаются из перевода в C: они выполняются на этапе
кодогенерации, и в сгенерированный код попадает уже вычисленное значение —
внутри секции допустимы конструкции, которые обычно не транслируются
(`#`, `&`, `..`). Значение «зашивается» на момент генерации и на шагах
модели не пересчитывается.

**Системные переменные** (доступны в любом скрипте без объявления):
`hmin`, `hmax` — минимальный и максимальный шаг интегрирования (сек);
`stepsize` — текущий шаг; `endtime` — время окончания расчёта.

## Функции языка — по реестру, не по догадке

Правдоподобные имена (`tan`, `asin`, `pow`) в языке **отсутствуют** — в
реестре справки таких записей нет. Существование имени проверяется по реестру
[`simintech_api/data/language_functions.json`](https://github.com/producedbysavant/simintech-code/blob/main/simintech_api/data/language_functions.json),
поиск по имени — `simintech_api.language.find_function`. Реестр отвечает, есть
ли такое имя, и даёт его назначение, но **не** даёт сигнатур — порядок
аргументов по нему не узнать; угаданное имя всплывёт только на кодогенерации.

## Область видимости и объявления

```simintech
input u: double;
output y: double;
const k = 2.5;
var counter: integer;

begin
    y = u * k;
end;
```

Правила:

- **Регистр не различается**: `Speed` и `speed` — одно и то же
- **У каждой переменной явный тип**: `var a: double, b: double;`
- **Запрещены имена `i`, `j`, `c`** — конфликтуют с авто-счётчиками транслятора
- `var` сохраняет значение между расчётными шагами
- Код исполняется на каждом расчётном шаге

## Типы

| Тип | Кодогенерация |
|---|---|
| `double`, `integer`, `boolean` | ✅ |
| `array`, `intarray` (только статические) | ✅ |
| `string` | ❌ не генерируется |
| `float` | ❌ имени типа нет: `var x: float` не компилируется сам по себе |

Координаты (`xcoord`, `ycoord`, `getportpoint`, `getwirestartpointcoord`) —
тип `point`; принимать их можно **только** в `double` (`point` в `integer` не
присваивается). Изоляция 04.10.2026: `var d: double; d = xcoord(q);` собирается
и `floattostr(d)` печатает числа; та же пара с `float` — not-compiled, а текст
ошибки виден только в окне сообщений редактора (через COM не читается).

## Комментарии

`{ ... }` — блочный, `//` — до конца строки.

## Подводный камень: генерация Pascal-кода в `.inc`

Если строите Pascal-код строками в секции `beforecompile`, у языка выражений
**нет экранирования кавычек** — литерал `"` внутри строки закрывает её
досрочно, и остаток кода парсится как выражения. Симптом: «Символ X не может
быть использован» или «Ключевое слово if задано неверно» для символа, который
виден внутри строки.

Правило: одна строка — одно выражение; для встраиваемых Pascal-литералов
используйте `quotes = chr(34)`, для переводов строк — `CLRF`.

## Построение модели встроенным языком

**Путь, который вендор называет для сборки схемы.** В ответе технической
поддержки (2026-09-28) для сборки схемы из скрипта назван именно встроенный
язык, а не вызовы построения через COM; в наших документах тот же механизм
описан как **альтернативный** (`simintech-code`, `docs/architecture.md`) —
выбирайте по задаче. Цикл задуман из `createblock` и трёх функций текста модели:

| Функция | Что делает | Чем подтверждена |
|---|---|---|
| `createblock` | Создать блок по **имени класса** из подключённой библиотеки (полное имя записи); отказ — `0` | справка; сам ноль — замером на установке во время расчёта |
| `savemodeltofile(projectid, path)` | Выгрузить текущий контейнер в текст — на всю глубину, вместе со свойствами страницы и её скриптом | живой замер 2026-09-28 |
| `createmodel(projectid, model)` | Создать модель из декларативного текста | живой замер 2026-09-29: пять демонстрационных проектов вендора и своя проба |
| `createmodelfromfile(projectid, path)` | Создать модель из текстового файла | живой замер 2026-09-29 (BOM файлу не нужен) |

**Семейство функций текста модели вендор называет из четырёх имён** (второй
ответ технической поддержки, 2026-09-28): `createmodel`, `createmodelfromfile`,
`savemodeltofile` и `savemodeltotext`. Последней в поставке 2.26.6.23 мы не
нашли: в срезе справки её нет, но нет там и `savemodeltofile` с
`createmodelfromfile`, которые живым вызовом отвечали, — поэтому считать её
существующей не на чем, и в сценарии на это имя пока не опираются. В описанный
выше цикл она не входит.

`createblock` есть и в официальной справке
([createblock](https://help.simintech.ru/11_yazyk_programmirovaniya/6_funkcii/3_graficheskie_i_sistemnye/obekty/createblock.html)):
`obj_id = createblock(id, class_name)`, есть варианты с владельцем
(`parent_id`) и номером слоя (`layer_nmb`); класс берётся из подключённой
библиотеки, имя — **с учётом регистра**. Требование к имени то же, что у COM:
полное имя записи, а не короткий заголовок с палитры
(см. `simintech-model-building`).

Ни одно из четырёх имён в срезе справки вендора (2026-05-15, 878 имён) не
встречается; пришли они из ответов технической поддержки. На `savemodeltotext`
по-прежнему **не опира**емся: в поставке 2.26.6.23 его не нашли. Остальные три
**проверены живым замером 2026-09-29** на поставке 2.26.6.23: `savemodeltofile`
выгружает контейнер и отдаёт образец синтаксиса, `createmodel` и
`createmodelfromfile` объекты создают — проходят все пять демонстрационных
проектов вендора (`Demo/Язык программирования/Функции/Создание схем из скрипта
createmodel`) и собственная проба. Форма аргумента `createmodel` — именованный
кортеж, **объявленный в тексте скрипта** (`const model : ( Имя: ( … ), … );`),
а не строка.

**Ловушка, из-за которой загрузка выглядела сломанной** (наш прежний
отрицательный результат — ошибка на нашей стороне): кавычка внутри строкового
литерала задаётся `chr(34)`. Удвоение `""` в этой сборке даёт **пустую строку**,
а обратный слэш не экранирует; текст модели при этом выглядит правдоподобно,
объектов не создаёт и сообщений не оставляет. BOM файлу не нужен:
`createmodelfromfile` его принимает, а вклейка через `eval` — нет (BOM попадает
в исходник).

Порядок «выгрузить → поправить → загрузить» проверен целиком, но успехом
считайте **появление объектов** (`list_blocks`), а не отсутствие ошибки:
отдельного сигнала «текст не принят» у среды нет.

Доставка скрипта в проект — отдельный риск: COM-метод `SetPageScript` кладёт код
в **текущую** страницу и возвращает `1` даже при синтаксически неверном скрипте,
а ошибка наружу не сообщается вовсе. **Признак успеха — не код возврата и не
один лишь файл:** ошибка времени выполнения молча обрывает остаток скрипта и
оставляет файл неполным, поэтому проверок две — пара маркеров начала и конца в
файле результата **и** рост модельного времени (нерастущее время означает, что
скрипт не скомпилировался и расчёт не пошёл). Контракт с тремя обязательными
проверками описан в
[simintech_api/core/script_bridge.py](https://github.com/producedbysavant/simintech-code/blob/main/simintech_api/core/script_bridge.py).

**Доставка есть — и ставит тело в `initialization`.** Инструменты MCP-сервера
(`set_page_script`, `run_page_script`, `inject_submodel_script`) выполняют текст
именно в этой секции — там, где создавать объекты разрешено, — и **возвращают
прежний скрипт страницы на место** в том же вызове. Прежняя проба
`ScriptBridge.run_probe` ставила тело под `if firststep then`, то есть в момент,
когда создавать объекты уже запрещено: для сборки модели она не годится, а
`ScriptBridge.install_script` стирает прежний скрипт, не сообщая, что там было.
Разбор исходов и порядок шагов — в разделе «Контур: как код доезжает до проекта».

Файл, по которому проверяете успех, держите в каталоге результатов
(`SIMINTECH_OUTPUT_DIR`): вне его `read_output_file` файла не увидит, а
относительный путь в скрипте разрешается от рабочего каталога приложения.

## Контур: как код доезжает до проекта

Скрипт в проект доставляет **MCP-сервер** (`simintech-mcp`): он ставит текст в
скрипт текущей страницы, запускает расчёт и читает файл результата. Инструменты —
`get_page_script`, `set_page_script`, `run_page_script`, `inject_submodel_script`,
`export_model_text`, `import_model_text`; прежний скрипт страницы возвращается на
место, а изменения модели живут в памяти до `save_project`.

**Среда молчит об ошибках скрипта.** `SetPageScript` возвращает `1` даже при
синтаксически неверном тексте, ошибка времени выполнения молча обрывает остаток
скрипта, а текст ошибки компиляции виден только в окне сообщений редактора
SimInTech — через COM он не читается. Поэтому инструменты не «верят» коду
возврата, а различают **пять исходов** по маркерам, которые сам скрипт пишет в
файл результата (`CTX_BEGIN` до тела, `CTX_END` после), и по росту модельного
времени:

| Исход | Что это значит | Что делать |
|---|---|---|
| `ok` | тело дошло до конца, расчёт идёт | читать строки тела из ответа |
| `model-not-running` | скрипт собрался и отработал, а **модель не считает** | проверить соединения: неподключённый вход останавливает расчёт всей модели молча; это не ошибка скрипта |
| `aborted` | обрыв на исполнении: начальный маркер есть, конечного нет | в ответе — последняя записанная строка; искать ошибку времени выполнения в теле |
| `not-compiled` | скрипт **не собрался** (маркеров нет, время стоит) | текст ошибки — в окне сообщений редактора SimInTech; чаще всего это забытая точка с запятой или кавычка не через `chr(34)` |
| `section-not-run` | маркеров нет, но расчёт шёл | секция `initialization` не выполнилась; сообщается как есть, причина по этому признаку не определяется |

**Порядок шагов задания.** Собирать модель текстом:

1. `export_model_text` — посмотреть, что уже есть на текущей странице (заодно
   образец синтаксиса для шага 3);
2. `import_model_text` — собрать объекты из текста; `createmodel` **дополняет**
   модель, старые объекты остаются;
3. сверить результат по отчёту об изменениях в ответе (сколько объектов было и
   стало, какие добавились) — «нет ошибки» успехом не считается;
4. `set_calc_time` → `run` → `read_output_file` — расчёт и снятие результата;
5. `get_page_script` — посмотреть, какой скрипт лежит на странице (чтение
   **не запускает** расчёт и не сдвигает модельное время).

**Скрипт пишут только тогда, когда текста модели не хватает** (сбор данных,
создание объекта определённого типа). Для этого `set_page_script` — он
проверяет, что скрипт собрался, и возвращает прежний текст; `inject_submodel_script` —
субмодель со скриптом сбора данных, который исполняется на каждом шаге расчёта;
`run_page_script` — произвольное тело в секции `initialization` (клапан, для
разведки и нестандартных случаев).

**Сбор данных: три вещи, которые не выводятся из текста скрипта** (замер
2026-09-29). Присвоенный субмодели скрипт исполняется на каждом шаге, но файл,
открытый в `initialization`, к телу уже не тот, а сам он держит блокировку —
файл сбора остаётся залоченным процессом SimInTech. Поэтому файл открывают и
закрывают **в теле на каждом шаге**, дописывают через `seek(fw, filesize(fw))`
(режимы создания и записи усекают файл), а `filesize` принимает **дескриптор**,
не имя. Субмодель остаётся в проекте и пишет дальше — для длинного сбора гоняйте
расчёт после инжектирования.

**Три запрета, которые контур не обходит.** Создавать объекты можно только в
секции `initialization` — инструменты ставят тело туда, а `finalization` при
внешней остановке расчёта не срабатывает, поэтому данные собирают записью в
теле. Кавычка внутри строкового литерала — только `chr(34)`. Удалять объекты в
живом проекте нельзя: `removeprimitiv` роняет следующий старт расчёта (access
violation в `mbtylib.dll`).

**Полный сценарий с численной приёмкой и падающими случаями** —
[`docs/examples/language-contour.md`](https://github.com/producedbysavant/simintech-mcp/blob/main/docs/examples/language-contour.md)
в репозитории MCP-сервера: реплики агента, что сверяет человек, и четыре
случая, на которых контур обязан отказать внятно.

## Декларативный текст модели

Записи «симулинковского вида»: объект — имя, класс, точки и свойства; провод —
отдельная запись со ссылками на порты концов; вложенный контейнер — вложенная
запись.

```text
Имя: (type = "Класс", points = [...], свойства)
Имя: (type = "wire", src = "block:out:0", dst = "block:in:0")
Имя: (type = "Субмодель", points = [...], subsystem: ( … ))
```

Как это читается: `type` — класс из библиотеки; `points` — точки объекта на
схеме; остальные поля внутри скобок — свойства блока, и имена у них сверяйте с
каталогом (`simintech-model-building`), а не с догадкой. В `src` и `dst` порт
адресован тремя частями: имя блока, сторона (`out`/`in`) и номер порта.
`subsystem` — **вложенное поле** записи субмодели: `type = "Субмодель"` остаётся
на месте, а содержимое её страницы лежит внутри `subsystem:` своим уровнем
вложенности (так в демонстрационном проекте вендора, `Demo/Язык
программирования/Функции/Создание схем из скрипта createmodel`).

Полей здесь ровно столько, сколько нужно, чтобы прочитать выгрузку. Остальное
даёт `savemodeltofile` на реальном контейнере — не догадка.

## Скрипт внутри субмодели: инжектирование

Приём из примера вендора (`Инжектирование скрипта в пакет через субмодель`; в
поставке 2.26.6.23 папки с примером нет) — присвоить субмодели свой скрипт
динамически. Замер 2026-09-29: **без третьего шага скрипт не компилируется**, и
снаружи это выглядит как «присвоили — и ничего не происходит», без сообщений.

```simintech
// фрагмент внутри секции initialization скрипта страницы
const SUB_MODEL_CODE = 102;
var objid: integer;

objid = createprimitiv(SUB_MODEL_CODE, [(0, 0), (-16, 0), (0, -16), (0, 16)]);
setprop(objid, "script", script_text);
reinitsubmodel(objid);   // компиляция скриптов субмодели — обязательный шаг
```

Число `102` — код типа объекта «субмодель» (`otSubModel`); текст присваиваемого
скрипта собирают строкой заранее и подставляют переменной.

[reinitsubmodel](https://help.simintech.ru/11_yazyk_programmirovaniya/6_funkcii/3_graficheskie_i_sistemnye/sistemnye/reinitsubmodel.html)
— «переинициализация и компиляция скриптов определённой субмодели». После неё
присвоенный скрипт исполняется на каждом шаге расчёта, и `seterrorstr` внутри
него работает.

Что внутри присвоенного скрипта работает **не так** (замеры 2026-09-29,
2.26.6.23):

- `floattostr(time)` записи не даёт — файл создаётся, но остаётся пустым; при
  этом `seterrorstr("Time = " + time)` (формула вендора) компилируется и
  исполняется. Значение `time` здесь считать нечем;
- `finalization` не срабатывает при остановке расчёта извне; при естественном
  окончании не проверена. Поэтому данные собирают записью в файл **в теле
  скрипта**, а не в `finalization`.

**Внешние порты субмодели видны сразу.** `initsubmodelports(sub)` пересобирает
их по блокам «Порт входа»/«Порт выхода» внутри субмодели: замер даёт
`getblockportcount` = 0 до вызова и 2 **сразу после**, ещё в `initialization`.
До этой находки порты приходилось читать на первом шаге расчёта.

## Обход модели: контейнеры, объекты, порты

Иерархия читается не только выгрузкой текста: контейнер перечисляется по
индексу, а вверх по уровням ведут владельцы страниц. Так сделано в
демонстрационных проектах вендора — обход **вниз** в «Конечных автоматах»
(`Пример 0.prt`), подъём на уровень в
`Demo/Приёмы работы/Получение данных, доступа и т. п./Получение имени субмодели
через уровень при помощи submodelbypageid`.

| Функция | Что даёт |
|---|---|
| `getsubmodelid(block)` | страницу (контейнер) субмодели — с ней работают `createblock`, `createwire`, `getobj`, `getobjcount` |
| `getobjcount(contid)` | число объектов в контейнере; считает и служебные объекты и обновляется не всегда сразу, поэтому на него не опираются как на меру «что создалось» |
| `getobj(contid, i)` | id объекта по индексу; индекс **с единицы** — `for (i = 1, num)` |
| `getownercontainer(obj)` | контейнер-владелец объекта (страница) |
| `submodelbypageid(page)` | блок субмодели, которому принадлежит страница |
| `findstartport(port)` | первичный выходной порт по входному |
| `getportblockid(port)` | блок-владелец порта |
| `getfullname(obj)` | полный путь объекта в проекте |

Подъём на уровень — цепочкой: `getownercontainer(block)` →
`submodelbypageid(page)` → `getownercontainer(…)` и так выше. Ноль в ответе —
тот же молчаливый отказ, отличить его от «объекта нет» нечем.

## Ветвление: `src = "имя_линии:K"`

Ветвь отходит не от блока, а от **точки** уже существующей линии: в `src`
пишется имя родительской линии и номер точки, **с нуля**.

```text
branch_0: (type = "wire", src = "wire_0:0", dst = "kx_1:in:0")
```

В COM той же паре соответствует `getparentwireid` (сама родительская линия) и
`getparentwirenodeindex` (номер узла), и там счёт **на единицу больше**: точка
`K` из текста — это узел `K + 1` (`node = point_nmb + 1`). Число, взятое из
текста без поправки, укажет на соседний узел. Нумеруются при этом **точки
линии**, а не ветви: идентификатора ветвления `getparentwirenodeindex` не
возвращает, ветвь опознаётся родительской линией.

Обе функции работают **только с ветвлением**: если линия подключена к порту
блока или висит в воздухе, они возвращают `0` — это описание вендора, а не наш
замер. Ноль здесь значит «ветвления нет», а не «идентификатор неизвестен», —
отличить его от ошибки вызова нечем. Отдельного объекта «ветвление» в проекте не
появляется вовсе: его роль играет сама линия-родитель (второй ответ технической
поддержки, 2026-09-28; измерена нами только нумерация `K ↔ K + 1`).

**Без промежуточных точек ветви неразличимы.** У линии без точек перегиба все
ветви ссылаются на одну и ту же запись линии, и отличить их нечем — место
отвода в записи не выражено. Поэтому место отвода задают **при создании линии**:
у вызова создания есть номер точки (`createwire(…, point_nmb, …)`), и подключать
ветви можно только к существующим точкам. Как именно эти точки выглядят в тексте
(`points` записи линии), берите из реальной выгрузки `savemodeltofile`: форма
сегментов из неё не восстанавливается, и достаточность выгрузки для дерева
сегментов не проверялась.

## Тип объекта — число из `getobjtypeid`

Тип объекта читается функцией `getobjtypeid`, и это единственный источник:
вендор называет те же числа константами (второй ответ технической поддержки,
2026-09-28) — `otBlock` = 100, `otWire` = 101, `otSubModel` = 102,
`otBlockPort` = 103, `otToMem` = 104, `otFromMem` = 105, `otWatchPoint` = 106,
`otLineBlock` = 107, `otLabel` = 108, `otNewBlock` = 109, `otCtrlPoint` = 110,
`otBridge` = 111, `otInOut` = 112, `otNode` = 113, `otImageFrameBlock` = 114.

Сверяйте число с таблицей
[getobjtypeid](https://help.simintech.ru/11_yazyk_programmirovaniya/6_funkcii/3_graficheskie_i_sistemnye/obekty/getobjtypeid.html),
а не с догадкой: там те же числа с теми же именами. Ветвь — это линия (101), а не
блок, и в адресации портов она не участвует.

## Правила среды: где отказ молчаливый

Замеры 2026-09-28 … 2026-10-01, поставка 2.26.6.23. Ни одно из этих правил не
видно из текста скрипта: среда либо пишет в окно сообщений, либо молчит —
отказ приходит нулевым id, а не ошибкой.

- **Создавать объекты можно только в секции `initialization` скрипта страницы.**
  Её операции выполняются один раз при запуске расчёта
  ([initialization](https://help.simintech.ru/11_yazyk_programmirovaniya/5_klyuchevye_slova/sekcii/initialization.html)),
  всё вне секции идёт на каждом шаге — и создавать объекты тогда нельзя: среда
  отвечает «Установка блока на схему в процессе моделирования запрещена», а
  `createblock` возвращает `0`, то есть отказ выглядит как обычный нулевой id.
- **`createprimitiv` доступна только в графическом контейнере.** Из макроса
  среда отвечает «Функция createprimitiv не найдена»; вендорская справка и
  перечисляет её среди
  [функций, доступных только в графическом контейнере](https://help.simintech.ru/11_yazyk_programmirovaniya/funkcii_dostupnye_tolko_v_graf_konteinere.html).
  По блочному коду она создаёт объект **без портов**: порт задаётся отдельно —
  `setprop(obj, "PortNames", "<имя>")`, затем `initobject(obj)`. «Порт появился»
  ≠ «блок работает»: класс объекта остаётся внутренним (`FromMem`, `NewBlock`), а
  участие такого объекта в расчёте не измерялось.
- **`TAB` — предопределённая константа.** Присваивание `TAB = …` в секции ломает
  компиляцию скрипта, и видно это **только в окне сообщений**: через COM оно не
  читается, а расчёт при этом стартует молча. Проверить заранее нечем — имя
  `TAB` под свою переменную просто не занимают. Признак отказа при этом
  доступен: модельное время не растёт — ровно на это отказывают `run`/`step`.
- **Внешние порты субмодели создаются на её странице.** `getsubmodelid` даёт
  страницу субмодели, `createblock(contid, "Порт входа")` и `"Порт выхода"` —
  сами порты. Видны они **сразу**, если после создания позвать
  `initsubmodelports(sub)` (замер 2026-09-29: `getblockportcount` 0 → 2 ещё в
  `initialization`); без этого вызова порты появлялись только к первому шагу
  расчёта, и подтвердить их существование было нечем.
- **`traceallports(port)` по умолчанию обходит сопряжённые порты** — соседей
  видно в том числе в субмодели, за границей контейнера. Выключает этот обход
  явный `0` — остаётся только внешний сосед. В исходнике
  вендора `aWithCoPorts` инициализируется как `True` и переопределяется, только
  если аргумент передан, поэтому и форма из справки — `traceallports(port_id)` —
  это обход **с** сопряжёнными портами. Вариант с двумя аргументами измерен
  2026-09-28; утверждение про default — из исходника вендора того же дня
  (одноаргументную форму живьём не звали).
- **Порядок соседей в ответе `traceallports` — не контракт.** Вендор описал
  построение листа (корень линии всегда первый, затем рекурсивный обход в
  глубину, затем сопряжения с обоих концов) и оговорил: для сложных топологий
  порядок не гарантирован, а «первым идёт источник входа» верно только для
  топологий **без служебных блоков**, то есть без блоков с сопряжёнными портами
  («в память», «из памяти», порты субмоделей, шины). Брать первого соседа как
  признак направления — приём вендорского частного случая, а не правило, на
  которое можно опираться в модели со служебными блоками (второй ответ
  технической поддержки, 2026-09-28).
- **Удаление объекта: `removeprimitiv(id)` работает, но роняет старт расчёта.**
  Объект, созданный в `initialization` (в замере — через `createmodel`), после
  `removeprimitiv` из контейнера исчезает, а следующий запуск расчёта аварийно
  завершает приложение: `ProjectStart` возвращает `Access violation … in module
  'mbtylib.dll'`. Воспроизведено 2026-09-29 на четырёх прогонах: с удалением —
  падение (в том числе когда сначала удалён провод), без удаления — расчёт идёт.
  Пока это не исправлено, удалять объекты в живом проекте нельзя.
- **Точка в имени — принадлежность текста модели, а не языка скрипта.**
  `object.property = value` из ответа вендора относится к декларативному тексту
  (`a.formula = 10`); в выражении скрипта точка недопустима — компилятор
  отвечает «В имени локальной переменной точка недопустима», а работа скрипта
  продолжается дальше, и присваивание молча не происходит. Из скрипта параметры
  пишут `setprop`/`setpropasstring`.
- **`setprop` пишет «Значение»; при живой «Формуле» запись маскируется.**
  У параметра два поля: «Формула» — то, что считает модель, и «Значение» —
  вычисленное. `setprop(obj, "a", …)` записывает «Значение», но если у
  параметра есть «Формула», ни чтение, ни пересчёт записи не видят — правка
  молча теряется (живой замер 02.10.2026: «Формула 3 / Значение 17.9954»).
  Формулу ставит и правит `setpropformula(obj, "a", "13.5")`, читает —
  `getpropformula`; COM-путь `SetBlockProp` (в MCP — `set_block_param`)
  пишет саму формулу — им правка формульного параметра не теряется
  (живой замер 02.10.2026, «Константа»: `set_block_param` 17 переписал
  `a.formula` с 13.5 на «17»).
- **Макрос в живом экземпляре — `mmain.exe "<проект.prt>" /projmacros
  "<макрос.txt>"`** (живой прогон 2026-10-01, поставка 2.26.6.23): проект
  открывается, макрос исполняется в нём, а `seterrorstr("…")` попадает в окно
  сообщений как [Информация]; при запуске из командной строки тот же лог виден
  в stdout (cp1251, строки `Time = … / Project = … / Info = …`; консольный
  вывод вендор включает для запуска из командной строки — `/nodialogs` не про
  это, а про диалоги закрытия). Форма поддержки `mstarter macros "файл"` —
  запускатель: справка вендора называет его назначением единственный экземпляр
  приложения (при уже запущенном аргументы уходят в него). В прогоне 2026-10-01
  без проектного контекста наблюдаемого исполнения получить не удалось.
  **Контекст макроса — не скрипт страницы**: `savemodeltofile` и
  функции ассистентского рантайма вендора (`getactiveprojectid`,
  `execandwait`) в макросе отсутствуют («функция не найдена» / «символ не
  может быть использован»). Из проверенного прогоном доступна `seterrorstr`
  (сообщение в логе); `initproject` и `runproject` есть в реестре имён, но
  живым вызовом не проверялись. `createprimitiv` из макроса недоступна — как
  в пункте выше («Функция createprimitiv не найдена»); прогон 2026-10-01
  строки ошибки не дал, но и объекта не показал — одиночный вопрос открыт.
- **`move(P, obj)` двигает рендер, не геометрию.** Сдвиг блока туда-обратно
  (+16/−16, и +32 у мультиплексора) не изменил выгрузку — ни точки блоков, ни
  провода; результат сбрасывается на шаге, персистентности нет (замер
  04.10.2026). Для изменения раскладки он не годится: позиции ставит
  `layout_place` (или координаты в тексте модели, `points`).
